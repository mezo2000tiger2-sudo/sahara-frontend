# Conversation feature: model specification

Status: implementation contract, not implemented code. Current backend source inspected on 28 October 2026. Read this file together with [essential-endpoints.md](./essential-endpoints.md).

## 1. Scope and naming

Use exactly four Mongoose models. Do not create `ConversationMessage`.

| Model | Collection | Implementation location | Change |
| --- | --- | --- | --- |
| `User` | `users` | `src/DB/models/user.model.js` | Existing; keep its schema unchanged. |
| `Message` | `messages` | `src/DB/models/message.model.js` | Existing; add `conversationId` and the constraints below. Store anonymous messages and chat messages here. |
| `IdentityRequest` | `identityrequests` | `src/DB/models/identity-request.model.js` | New. |
| `Conversation` | `conversations` | `src/DB/models/conversation.model.js` | New. |

Paths above are relative to `saharah_backend`, not the frontend containing these documents. Register the exact model names shown in the table so `ref` values resolve correctly. The collection names are the corresponding default Mongoose pluralizations.

**Use `Message.recevierId` exactly as currently spelled.** It is the receiver. `senderId` is already present in the backend. Older drawings use `userId` for the receiver; that name is obsolete for this implementation contract. Do not add a second receiver field or rename the existing field as part of this feature.

Do not add `originalMessageId`, `isOriginal`, a message `kind`, or a duplicate copy of the selected message. When identity is accepted, assigning `conversationId` makes that Message an ordinary conversation message.

## 2. MongoDB storage rules

- **REFERENCE:** store another document's ObjectId and use the exact Mongoose `ref` model name. Do not copy the referenced document into the field.
- **INLINE VALUE:** store the scalar or scalar array directly in the current document.
- **EMBEDDED MODEL DOCUMENTS:** none in this design. There is no embedded User, Message, Conversation, or IdentityRequest document.
- `participants` is an inline array of ObjectIds whose **relationship is a reference to User**. It is not an array of embedded User documents.
- `attachments` and `coverImages` are inline arrays of strings. They have no model reference or foreign-key relationship.
- A response may include nested safe profile JSON for display. That response shape does not mean User documents are embedded in the database.
- A `ref` does not enforce document existence, authorization, or cascade deletion. The endpoint services enforce those rules.

## 3. Common stored fields and schema options

All four models include these stored fields:

| Field | Type | Required/default | Uniqueness and meaning |
| --- | --- | --- | --- |
| `_id` | `ObjectId` | Automatically generated by Mongoose. | Unique primary identifier; built-in unique `_id` index. |
| `createdAt` | `Date` | Automatically set with `timestamps: true`. | Not unique. Creation timestamp. |
| `updatedAt` | `Date` | Automatically maintained with `timestamps: true`. | Not unique. Timestamp of the latest update. |
| `__v` | `Number` | Default Mongoose version key, initially `0`. | Not unique; not an application message sequence number. |

Keep `timestamps: true`, `strict: "throw"`, and `strictQuery: "throw"`. Leave the default version key enabled. Dates are stored as dates and serialized as ISO 8601 strings in API responses. ObjectIds are stored as ObjectIds and serialized as strings.

The existing User and Message schemas enable virtuals in object/JSON conversion. A virtual or Mongoose's `id` alias is not an additional stored database field. API responses must use explicit allowlists regardless of those options.

## 4. User: existing schema, unchanged

The following fields are in addition to the common stored fields above. Every field is an inline scalar or scalar array; none references another model.

| Field | Type | Required | Default | Unique | Constraints / storage |
| --- | --- | --- | --- | --- | --- |
| `fName` | `String` | Yes | None | No | Trim; 2–50 characters. |
| `lName` | `String` | Yes | None | No | Trim; 2–50 characters. |
| `email` | `String` | Yes | None | Yes | Trim, lowercase, existing email-format validator; unique index. |
| `phone` | `String` | No | None | No | Preserve existing storage behavior; do not expose through conversation profiles. |
| `role` | `String` | No explicit required flag | `"user"` | No | Enum: `"user"`, `"admin"`. Role does not grant access to other people's conversations. |
| `age` | `Number` | When `providor === "system"` | None | No | Minimum 18; maximum 60. |
| `password` | `String` | When `providor === "system"` | None | No | Preserve existing credential handling; never include in a feature response. |
| `gender` | `String` | No explicit required flag | `"male"` | No | Enum: `"male"`, `"female"`. |
| `avatar` | `String` | No | None | No | Existing avatar value; use only a safe display value in profile responses. |
| `coverImages` | `String[]` | No | `[]` | No | INLINE scalar array, not an embedded model or a reference. |
| `providor` | `String` | No explicit required flag | `"system"` | No | Enum: `"system"`, `"google"`, `"github"`. Preserve this existing spelling. |
| `isConfirmed` | `Boolean` | No | No explicit default | No | New authenticated feature endpoints require a confirmed account. |
| `changeCredentialsAt` | `Date` | No | None | No | Existing authentication invalidation timestamp. |

`fullName` is an existing non-stored virtual derived from `fName` and `lName`. Do not add a stored `fullName` field for this feature. Do not add message, request, or conversation ID arrays to User.

## 5. Message: one model for every message

Current fields: `content`, `attachments`, `recevierId`, `senderId`, and common stored fields. Proposed new field: `conversationId`.

| Field | Type | Required | Default | Unique | Relation / constraints |
| --- | --- | --- | --- | --- | --- |
| `content` | `String` | When `attachments` has no items | None | No | INLINE scalar; trim. At least nonblank text or one attachment must exist. Chat POST additionally limits text to 1–5000 characters. |
| `attachments` | `String[]` | No | `[]` | No | INLINE scalar array of server-controlled file values, not a referenced attachment model. Keep existing anonymous-upload support; new chat POST is text only. |
| `recevierId` | `ObjectId` | Yes | None | No | **SENT TO — REFERENCE `User`**. Make immutable for persisted messages. |
| `senderId` | `ObjectId` | Required for messages belonging to a conversation; optional for standalone guest/legacy messages | None | No | **SENT BY — REFERENCE `User`**. Server assigns it from the authenticated user. Make immutable; use `select: false` as a query default, plus safe response serialization. |
| `conversationId` | `ObjectId` | No | `null` | No | **BELONGS TO — REFERENCE `Conversation`**. A message belongs to at most one conversation. |

### Message invariants

1. Preserve guest anonymous sending. A standalone guest message has no known `senderId`; do not invent one or backfill it from the receiver.
2. A message without a sender cannot receive an identity request or enter a conversation under this feature.
3. A new authenticated standalone message gets `senderId` from the session, `recevierId` from validated existing send input, and `conversationId: null`.
4. A chat message must have a sender and receiver matching the two participants, with sender and receiver distinct. Its sender and receiver are derived by the server, not accepted from the chat POST body.
5. A standalone message may change from `conversationId: null`/missing to one conversation ID after acceptance. Once assigned, it cannot be reassigned or cleared by this feature.
6. **Do not mark `conversationId` immutable in the schema:** that would prevent the required null-to-ID transition. Enforce its one-time assignment with a conditional service update inside the acceptance transaction.
7. The selected message and subsequent replies have exactly the same stored shape. Query all chat history by `conversationId`; do not classify the selected message separately.
8. `senderId` is private before acceptance. `select: false` does not sanitize newly created documents or aggregation results; use explicit response objects. After membership is verified, chat responses may expose the author ID.
9. The current backend's `attachments?.length` check is already spelled correctly. Do not reapply an old typo fix from an earlier diagram.

## 6. IdentityRequest: new

| Field | Type | Required | Default | Unique | Relation / constraints |
| --- | --- | --- | --- | --- | --- |
| `messageId` | `ObjectId` | Yes | None | **Yes** | **REQUESTS IDENTITY FOR — REFERENCE `Message`**. Immutable. One lifetime request per message. |
| `status` | `String` | Yes | `"pending"` | No | Enum: `"pending"`, `"accepted"`, `"rejected"`. |

Include the common stored fields. Do not store `requesterId`, `senderId`, participant profiles, or `conversationId` here. Derive them through the referenced Message:

- Requester = `Message.recevierId`.
- Decider = `Message.senderId`.
- Conversation after acceptance = `Message.conversationId`.

Allow only `pending → accepted` or `pending → rejected`. Same-decision retries return the current result; opposite terminal decisions return 409. Repeating request creation returns the existing request and must not reset its status. These transitions are enforced by the service; an enum alone does not enforce them.

## 7. Conversation: new

| Field | Type | Required | Default | Unique | Relation / constraints |
| --- | --- | --- | --- | --- | --- |
| `participants` | `ObjectId[]` | Yes; exactly two entries | Mongoose array default `[]`, which must fail the two-participant validator until populated | **No** | **HAS PARTICIPANTS — ARRAY OF REFERENCES `User`**. Exactly two distinct IDs; immutable membership. No embedded User objects. |

Include the common stored fields. There are no other feature fields on Conversation.

The acceptance service constructs `participants` from the selected Message's `senderId` and `recevierId`. Verify both users exist and are different. Reject invalid/missing related data instead of creating a partial conversation.

Use a model validator for exactly two distinct ObjectIds. Service writes and endpoint input validation must also prohibit participant replacement, addition, or removal. Do not provide a participant-management endpoint.

Do not add a uniqueness constraint to `participants` or to the participant pair. The same user may participate in many conversations, and independently accepted messages may create separate conversations between the same pair. Acceptance retries must still return the same conversation for that request.

Do not store `originalMessageId`, `requestId`, `messageIds[]`, `messages[]`, copied profiles, or embedded message history. Message documents reference the conversation instead.

## 8. Complete relationship map

| Name | Stored reference | Type | Cardinality |
| --- | --- | --- | --- |
| **SENT TO** | `Message.recevierId → User._id` | REFERENCE | Every Message has one receiver; a User may receive zero or many Messages. |
| **SENT BY** | `Message.senderId → User._id` | REFERENCE | A standalone guest Message may have no known sender; every chat Message has one sender. A User may send zero or many Messages. |
| **BELONGS TO CONVERSATION** | `Message.conversationId → Conversation._id` | REFERENCE | A Message belongs to zero or one Conversation; a valid committed Conversation starts with one Message and can contain many. |
| **HAS PARTICIPANTS** | `Conversation.participants[] → User._id` | ARRAY OF REFERENCES | Each Conversation has exactly two distinct Users; a User may participate in zero or many Conversations. |
| **REQUESTS IDENTITY FOR** | `IdentityRequest.messageId → Message._id` | REFERENCE | Every IdentityRequest targets one Message; a Message has zero or one IdentityRequest. |

All inter-model relationships are references. The inline string arrays have no connector to another model.

## 9. Required indexes and what must NOT be unique

| Collection | Index | Unique? | Purpose |
| --- | --- | --- | --- |
| All | `{ _id: 1 }` | Yes | Built-in document identity. |
| User | `{ email: 1 }` | Yes | Preserve existing email uniqueness. |
| Message | `{ recevierId: 1, conversationId: 1, createdAt: -1, _id: -1 }` | No | Anonymous inbox and stable date/ID sorting. |
| Message | `{ senderId: 1, conversationId: 1, createdAt: -1, _id: -1 }` | No | Standalone sent messages. |
| Message | `{ conversationId: 1, createdAt: -1, _id: -1 }` | No | Paginated chat history. |
| IdentityRequest | `{ messageId: 1 }` | **Yes** | Prevent duplicate requests, including concurrent creation. |
| Conversation | `{ participants: 1, createdAt: -1, _id: -1 }` | No | Current user's conversation list. |

The compound indexes intentionally match the current backend's date-then-ID sorting. Earlier drawings used shorter `_id`-only sort indexes; use this table for implementation. Do not create both versions unless a measured query requires it.

Do not make `senderId`, `recevierId`, `conversationId`, `participants`, or `status` unique. Many documents must be able to share these values.

Build and confirm actual indexes before enabling routes. Declaring `unique: true` describes an index; it is not a Mongoose validator. Catch expected duplicate-request errors without exposing raw MongoDB error details.

## 10. Atomic acceptance and access invariants

One transaction must claim a pending request, create its two-user Conversation, and assign the selected Message's `conversationId`. If any operation fails, none may persist. MongoDB must support multi-document transactions; deployment topology is not verified by these documents.

A retry uses `IdentityRequest.messageId → Message.conversationId` to find the already-created conversation. Do not introduce a special message field or create another conversation on retry. See the endpoint document for the precise decision algorithm.

Only the two stored participants can access a conversation, its message history, or its attachments through the application. Every read/write verifies membership; roles, guessed IDs, and client-supplied receiver IDs do not bypass this check. Mongoose `ref` or schema validation does not provide authorization.

No deletion/cascade workflow is added by this feature. Do not delete or guess references during migration. Preserve guest/legacy messages and existing User fields.

## 11. Implementation acceptance checks

- User schema and both existing field spellings remain unchanged.
- There are four models, no separate chat-message collection, and no special selected-message field.
- Arrays of strings remain inline; all five named inter-model relations use ObjectId references.
- Missing sender is allowed only for standalone messages; chat creation cannot save an unknown author or a third-party receiver.
- Conversation validates exactly two distinct existing users and cannot have membership edited through the feature.
- Unique `IdentityRequest.messageId` rejects duplicate database writes; repeated API creation returns the existing record.
- A null-to-ID conversation assignment succeeds only inside accepted consent; subsequent reassignment is rejected.
- Concurrent decisions and injected write failures preserve the atomic acceptance invariant.
- API serialization never exposes anonymous sender identity, private account fields, or raw storage paths.

These are requirements for the future implementation, not claims of live database or API testing.
